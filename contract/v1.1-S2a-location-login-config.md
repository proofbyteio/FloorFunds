### 3.0 Server-filled OIDC values [TLD 2026-11-04 7:41, UX D-51]

- Clients never send `oidc_authority` or `oidc_client_id`. Either key present in a PUT body or in `login_config` of a create → 422 `validation_failed` with field code `field_not_writable` (no event; A-15).
- The server fills both from deployment config, keys **`Entra:Authority`** and **`Entra:ClientId`** (DRAFT names), on create with `entra` and on any switch to `entra`. Entra → Entra edits keep the stored values (a deployment change does not silently rewrite rows; ASSUMPTION A-21). A switch to `database` nulls both (server-owned values, cleared by the server; this is not a silent clear of client data).
- `changed_fields` lists `oidc_authority` / `oidc_client_id` when the server sets or clears them.
- The admin API validates both deployment values at startup with the §5.2 rules (`oidc_authority` https base; `oidc_client_id` GUID); invalid or missing → it refuses to start (fail closed; A-21). Fixtures use fake client ids only.
- The DB constraint stays: entra ⇒ exactly one tenant + `oidc_authority` + `oidc_client_id` + `secret_ref` (§8.1).
- Only a **Super Admin** response shows `oidc_authority` / `oidc_client_id` (`login_config_view_super`); Partner Admin and org:V responses use `login_config_view_restricted`, which has neither key. MK9 shows them on a read-only card for Super Admin only.

### 3.2 `PUT /api/orgs/locations/{location_id}/login-config`

Permission: `org:location_login_method:write` [SRC: LD L171]. Headers: `If-Match: "<row_version>"` (required). Body: `$defs/login_config_write` = `provider_kind`, `display_name`, `entra_allowed_tenant_ids`, `secret_ref` (write-only), `mfa_required`, `allow_db_fallback`, `reason` [TLD 2026-11-04 7:41]. 200 returns the caller's view and the new `ETag`. Changes apply immediately [Confirmed DEC-096].

**Concurrency: ETag / If-Match, not a body field.** HTTP-native optimistic concurrency (RFC 9110 §13.1.1); keeps `row_version` out of the replacement body. **Missing `If-Match` → 428 `precondition_required`** (RFC 6585 §3). `If-Match: *`, a weak tag, a list, or a non-integer → 400 `if_match_invalid`. Stale → 409 `concurrency_conflict` with `current_row_version` (MK9 conflict banner).

`secret_ref`: **absent** = keep current; **string** = replace (rotation; `changed_fields` += `secret_ref`, no value); **null** = clear (only when switching to `database`). Switching an Entra location with a secret to `database` without `"secret_ref": null` → 422 `field_not_allowed` on `secret_ref`.

**Reason [TLD 2026-11-04 7:39, OQ-S2a-7]:** the server trims it. Blank (absent, null, whitespace-only) counts as no reason. A non-blank reason must be **10–500 characters after trimming**, else 422 `reason_length` (also when the change is not a downgrade). It is stored trimmed in the change row and the event. A downgrade with no reason → 400 `reason_required` (§4 step 10).

**Sessions [TLD 2026-11-04 7:41]:** sessions that are already signed in stay signed in after a method change; revocation is deferred (§12). The saved banner says so (MK9 939e41bd).

The caller is always checked before the value (TLD). First failing step wins; later steps don't run.

**Request id [TLD 2026-11-04 9:04, OQ-P3-3; name TLD 2026-11-04 9:20]:** every response (2xx, 4xx, 401, 500) carries `X-Request-ID`, a server-generated UUIDv7; a client-sent `X-Request-ID` (or any other id header) is ignored and never echoed. The header name is the one in frozen v1 `contract/errors.md` L67 (md5 1e97dae4d3da00c429d56c0f2f78464e) and `src/Login.StandIn/Allowlist.cs` L64 (md5 239a78993d177301f6528c68fd9afb62); neither file is changed. ### 8.3 RLS

- `ENABLE` + `FORCE ROW LEVEL SECURITY` on `location`, `location_login_config`, `location_login_config_change`.
- Per request, inside the transaction: `set_config('app.admin_type', 'super'|'partner', true)` and `set_config('app.partner_id', '<uuid>', true)` (transaction-local, pool-safe).
- **Trust boundary [TLD 2026-11-04 8:44, K4].** RLS here is defence in depth, not the authorisation decision. The `<db>_admin_api` role can call `set_config('app.admin_type', 'super', …)` itself, so the policies assume a **trusted API**: the API sets `app.admin_type` / `app.partner_id` only from the server-side authenticated identity (the validated `access_token_admin` and the server-side role lookup), never from request data (body, headers, query, path), and only **transaction-local** inside the request's transaction. `set_config(name, $1, true)` is used rather than the literal `SET LOCAL` statement: it has the same transaction-local semantics (`is_local = true`, reset at COMMIT/ROLLBACK, pool-safe) and, unlike `SET LOCAL`, takes a bind parameter, so no SQL text is ever built from a value. All SQL is parameterised. A compromised API process, or anyone holding the admin role's password, can read and write every partner's rows; separate DB roles per admin tier are backlog **V11-RLSROLES** (§12).
- Startup guard: the API refuses to start if its connection's role is a superuser, has BYPASSRLS, or owns the `auth` tables (the owner policy is `USING (true)`).
- Admin role policy on `auth.location`: `USING/WITH CHECK (current_setting('app.admin_type', true) = 'super' OR (current_setting('app.admin_type', true) = 'partner' AND partner_id = nullif(current_setting('app.partner_id', true), '')::uuid))`; on the other two via `EXISTS` on `auth.location` (itself filtered). Missing settings ⇒ no rows (fail closed). The server ALSO filters by `partner_id` in the query [SRC: LD L173].
- Login role policy: `FOR SELECT USING (true)` on `location` and `location_login_config` (not partner-scoped); no policy (and no grant) on the change table.
- Owner policy `USING (true)` so the two definer functions can see all rows under FORCE.
- Two `SECURITY DEFINER` functions (owner, `SET search_path = pg_catalog, auth`): `auth.location_partner(location_id) → partner_id` (steps 3–4) and `auth.tenant_bound_elsewhere(tid uuid, partner_id uuid) → bool` (step 8). **`REVOKE ALL ON FUNCTION … FROM PUBLIC`**, EXECUTE to the admin role only, and **`ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`** run as the owner (F4). It is global for the owner in this database, **not** `IN SCHEMA auth`: per-schema default privileges can only add to the global ones, so the `IN SCHEMA` form is a silent no-op (SSE correction found in P2 by a probe check; `pg_default_acl` is per database). Because it is global, it covers **every schema in this database**, including functions from extensions the owner installs later (they get no PUBLIC EXECUTE unless granted) [SSE2 P2-3].
- **RLS is OFF** on `app_user`, `external_login`, `user_location`, `audit_outbox`, `oidc_replay`, `session` (F7, SSE's call): the login service is not partner-scoped, grants enforce RO/RW, and an `ENABLE` with only a SELECT policy would break INSERT/UPDATE/DELETE. The admin role has no grant on any of them except INSERT on `audit_outbox`.

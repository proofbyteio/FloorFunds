### 3.0 Server-filled OIDC values and `secret_ref` [TLD 2026-11-04 7:41, UX D-51] [TLD 2026-11-04 9:49, D-51] [TLD 2026-11-04 10:02]

- Clients never send `oidc_authority` or `oidc_client_id`. Either key present in a PUT body or in `login_config` of a create → 422 `validation_failed` with field code `field_not_writable` (no event; A-15).
- The server fills both from deployment config, keys **`Entra:Authority`** and **`Entra:ClientId`** (DRAFT names), on create with `entra` and on any switch to `entra`. **Config is the source of truth [TLD 2026-11-04 10:02] (Q1):** the login reader (what SSE2's sign-in path and `ISecretResolver` are fed, §9) and the Super Admin view read `Entra:Authority`, `Entra:ClientId` and `Entra:SecretRef` from deployment config every time, never from the row. The row keeps a copy only because the DB constraint needs one (§8.1); nothing reads that copy (cleanup: V11-ROWSECRETCLEANUP, §12). A config change therefore applies to **all** entra locations after a restart, with no row rewrite. **Config is read once at startup; changes apply after a restart, no hot reload [TLD 2026-11-04 10:12].** Entra → Entra edits leave the copy untouched (no `changed_fields` entry for it). A switch to `database` nulls both (server-owned values, cleared by the server; this is not a silent clear of client data).
- `changed_fields` lists `oidc_authority` / `oidc_client_id` when the server sets or clears them.
- **`secret_ref` [TLD 2026-11-04 9:49, D-51] (TL 7:40 D-51 ruling: one app registration per deployment):** it comes from deployment config key **`Entra:SecretRef`** (DRAFT name), like `oidc_client_id`. The server sets `secret_ref` = `Entra:SecretRef` on create with `entra` and on a switch to `entra` (a non-authoritative copy, [TLD 2026-11-04 10:02] Q1: readers use `Entra:SecretRef` from config); Entra → Entra edits leave the copy untouched; a switch to `database` clears it. `changed_fields` lists `secret_ref` when the server sets or clears it (name only).

**Order of 408 / 413 vs 404 / 428 / 409 [TLD 2026-11-04 10:42] [TLD 2026-11-04 11:00]:** the body is read once, right after step 2, and nothing about the request is known until it has been read. **On PUT, 413 stays at step 7, after 404 / 428 / 409, per P3-3 [TLD 2026-11-04 9:28], which stands** (stale `If-Match` + oversize → 409; missing location + oversize → 404; no `If-Match` + oversize → 428). **On create, 408 and 413 come first** (before 404: the target partner is in the body). **408 comes first everywhere**: **401 / 403 stay first (TLD 9:04 #8) and 408 comes straight after them** [TLD 2026-11-04 11:19] (steps 1–2 never depend on the body); a read that gives up is answered at once, on PUT before 404 / 428 / 409. **Request id [TLD 2026-11-04 9:04, OQ-P3-3; name TLD 2026-11-04 9:20]:** every response (2xx, 4xx, 401, 500) carries `X-Request-ID`, a server-generated UUIDv7; a client-sent `X-Request-ID` (or any other id header) is ignored and never echoed. The header name is the one in frozen v1 `contract/errors.md` L67 (md5 1e97dae4d3da00c429d56c0f2f78464e) and `src/Login.StandIn/Allowlist.cs` L64 (md5 239a78993d177301f6528c68fd9afb62); neither file is changed. A 500 has no body; the id is the only handle. **[TLD 2026-11-04 9:28, P3-4]:** the header is set by middleware before routing, so responses outside the handlers carry it too (405 wrong method on a mapped path, unrouted 404).

**Oversize and unread bodies [TLD 2026-11-04 9:28, P3-2]:** the server parses at most 64 KiB of a body (bytes already buffered past the cap are discarded, never parsed); over that, 413 `payload_too_large`. Any response that leaves the request body unread (413, or a 401/403/404/405/409 that never needed it) carries `Connection: close`; after the response is flushed the server reads and discards at most 1 MiB more within 2 s, then closes, so the client receives the status line, headers and body instead of a connection reset. There is no server-wide body-size limit [TLD 2026-11-04 9:53/10:02, P3-10]: the former 1 MiB Kestrel setting was dead (lifted on every request) and is removed; every read is bounded by the API (size and time), and the framework's size limit and minimum data rate are lifted per request so one deadline governs. A client still sending after that bound sees its own writes fail after the response.

**Slow bodies, `Expect`, drain log [TLD 2026-11-04 9:53/10:02, P3-7/P3-8]:** a body the API reads is bounded in time as well (DRAFT 10 s for the whole body): not received in time → 408 `request_timeout` + `Connection: close` + `X-Request-ID`, nothing written, ONE Warning log line (`request_id`, no exception, no stack trace). A request with `Expect: 100-continue` and a `Content-Length` over 64 KiB gets 413 `payload_too_large` at once and never a `100 Continue` (the length is checked before the first read); an `Expect` request whose body was never read is not drained, and the server closes the connection right after the 413 is sent [TLD 2026-11-04 10:42] (the client has sent no body bytes, so it sees the full 413 and then a clean close, no reset; tested: bound < 1.5 s each, 200 repeats (100 PUT + 100 POST), 0 resets, every 413 received; Kestrel's own close took about 6 s). The close is done by setting **that request's** `MaxRequestBodySize` to 0 after the 413 is sent, so Kestrel closes the connection itself once the 413 is out; approved [TLD 2026-11-04 11:00] (a literal `ctx.Abort()` lost the 413 to a reset on some requests: build-log mutation MC2). The limit applies to that one request only: later requests on the same server (fresh connections, normal PUT and POST) keep the normal 64 KiB limit (tested). **Total deadline [TLD 2026-11-04 10:58 F-B1]:** the 10 s body deadline runs from the start of the body read and is never reset by a read: a body under 64 KiB whose `Content-Length` is never reached, trickled 1 byte every ~2.9 s, gets 408 at ~10 s (tested bound 9.5–11.5 s), `Connection: close`, `X-Request-ID`, nothing written, one Warning. The `<db>_admin_api` role can call `set_config('app.admin_type', 'super', …)` itself, so the policies assume a **trusted API**: the API sets `app.admin_type` / `app.partner_id` only from the server-side authenticated identity (the validated `access_token_admin` and the server-side role lookup), never from request data (body, headers, query, path), and only **transaction-local** inside the request's transaction. `set_config(name, $1, true)` is used rather than the literal `SET LOCAL` statement: it has the same transaction-local semantics (`is_local = true`, reset at COMMIT/ROLLBACK, pool-safe) and, unlike `SET LOCAL`, takes a bind parameter, so no SQL text is ever built from a value. All SQL is parameterised. A compromised API process, or anyone holding the admin role's password, can read and write every partner's rows; separate DB roles per admin tier are backlog **V11-RLSROLES** (§12).
- Startup guard: the API refuses to start if its connection's role is a superuser, has BYPASSRLS, or owns the `auth` tables (the owner policy is `USING (true)`).
- Admin role policy on `auth.location`: `USING/WITH CHECK (current_setting('app.admin_type', true) = 'super' OR (current_setting('app.admin_type', true) = 'partner' AND partner_id = nullif(current_setting('app.partner_id', true), '')::uuid))`; on the other two via `EXISTS` on `auth.location` (itself filtered). - Login role policy: `FOR SELECT USING (true)` on `location` and `location_login_config` (not partner-scoped); no policy (and no grant) on the change table.
- Owner policy `USING (true)` so the two definer functions can see all rows under FORCE.
- Two `SECURITY DEFINER` functions (owner, `SET search_path = pg_catalog, auth`): `auth.location_partner(location_id) → partner_id` (steps 3–4) and `auth.tenant_bound_elsewhere(tid uuid, partner_id uuid) → bool` (step 8). **`REVOKE ALL ON FUNCTION … FROM PUBLIC`**, EXECUTE to the admin role only, and **`ALTER DEFAULT PRIVILEGES REVOKE EXECUTE ON FUNCTIONS FROM PUBLIC`** run as the owner (F4). - **RLS is OFF** on `app_user`, `external_login`, `user_location`, `audit_outbox`, `oidc_replay`, `session` (F7, SSE's call): the login service is not partner-scoped, grants enforce RO/RW, and an `ENABLE` with only a SELECT policy would break INSERT/UPDATE/DELETE.
